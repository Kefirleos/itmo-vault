## 📌 Краткое резюме (TL;DR)

1. **В первых лабораторных используется C-API работы с файлами** (`<cstdio>`): по требованиям лаб нужны обычные массивы, без динамической памяти и `std::string`. C-API к тому же приучает явно закрывать файлы.
2. **`fopen(path, mode)`** возвращает `FILE*`; при ошибке — **`nullptr`**, его **обязательно** проверять. `path` — это **путь** (относительный или абсолютный), а не просто имя.
3. **`fgetc` возвращает `int`, а не `char`**, чтобы помимо любого байта уметь вернуть особое значение **`EOF`** (обычно `-1`) — конец файла или ошибку.
4. **Канонический цикл:** `while ((c = std::fgetc(f)) != EOF) { ... }`.
5. **`fread(buf, size, count, f)`** читает до `count` элементов размера `size` и возвращает, **сколько реально прочитал**; `0` — читать больше нечего.
6. **`fread` с буфером в ~20 раз быстрее `fgetc`**, но не потому, что `fgetc` «не буферизирован»: у `FILE` **уже есть** внутренний буфер. Разница — в **накладных расходах на каждый вызов** (в частности, блокировка `FILE` для потокобезопасности).
7. **Увеличивать буфер выгодно до предела:** после нескольких килобайт время упирается в обработку данных, а не в системные вызовы. Оптимум — **порядка 1–8 КиБ**, лучше кратно степени двойки.
8. **Файлы нужно закрывать (`fclose`)**: запись тоже буферизирована, и без `fclose` / `fflush` данные могут не попасть на диск. Позже автоматизировать это поможет идиома **RAII**.
9. **`fseek` / `ftell` / `rewind`** перемещают позицию чтения. Без `rewind` повторное чтение того же `FILE*` сразу упрётся в `EOF` — так ведущий сам ошибся в замерах.

## 1. Открытие файла: `fopen`

```cpp
#include <cstdio>

std::FILE* f = std::fopen("data.txt", "r");
if (!f) {                       // fopen вернул nullptr
    std::printf("No such file\n");
    return 1;
}
// ... работа с файлом ...
std::fclose(f);
```

- **Сигнатура:** `FILE* fopen(const char* filename, const char* mode)`. Обе строки — C-строки, т. е. указатели на первый символ, оканчивающиеся `'\0'`.
- **`filename` — путь к файлу:** `"data.txt"` (относительно текущего каталога), `"./data.txt"`, `"/home/user/proj/data.txt"` (абсолютный).
- **`FILE`** — структура стандартной библиотеки. Её устройство знать не нужно: все функции работы с файлами просто принимают `FILE*`.
- **Ошибка открытия** (нет файла, нет прав) → `nullptr`. Пользователь может передать что угодно, поэтому проверка обязательна.

### 1.1. Режимы открытия

| Режим | Назначение | Если файла нет | Если файл есть |
|:---|:---|:---|:---|
| `"r"` | чтение | ошибка (`nullptr`) | читаем с начала |
| `"w"` | запись | создаётся | **очищается** |
| `"a"` | дозапись в конец | создаётся | пишем в конец |
| `"r+"` | чтение и запись | ошибка | без очистки |
| `"w+"` | чтение и запись | создаётся | очищается |
| `"rb"`, `"wb"` … | то же, в **двоичном** режиме | — | — |

Полный список и тонкости — на [cppreference: fopen](https://en.cppreference.com/w/cpp/io/c/fopen).

## 2. Посимвольное чтение: `fgetc`

### 2.1. Почему `int`, а не `char`

`fgetc` (и её «двойник» `getc`, который стандарт разрешает реализовать макросом) возвращает:
- при успехе — прочитанный символ как `unsigned char`, преобразованный в `int` (`'a'` → `97`);
- при конце файла или ошибке — **`EOF`**, макрос с отрицательным значением, на практике `-1`.

> [!important] Зачем тип шире `char`
> Байт может принимать **все** 256 значений, поэтому «свободного» значения для сигнала об ошибке внутри `char` нет. Тип `int` вмещает и любой байт, и `EOF`. Сохранять результат `fgetc` в `char` — классическая ошибка: сравнение с `EOF` станет ненадёжным.

### 2.2. Канонический цикл

```cpp
int c;
while ((c = std::fgetc(f)) != EOF) {
    std::putchar(static_cast<char>(c));   // вывести файл в консоль
}
```

**Почему это работает.** Присваивание `c = std::fgetc(f)` — **выражение**, и его значение равно присвоенному. Поэтому в одном условии происходят два действия: (1) прочитать символ и сохранить в `c`; (2) сравнить его с `EOF`. Скобки вокруг присваивания обязательны: у `!=` приоритет выше, чем у `=`.

> [!tip] Инициализация переменных
> Переменную, к которой потом **прибавляют** (`count += ...`), нужно инициализировать: `std::size_t letters = 0;`. Переменную, которой сразу **присваивают** значение (как `c` выше), можно не инициализировать.

### 2.3. Пример: сколько в файле букв

```cpp
#include <cctype>
#include <cstddef>
#include <cstdio>

std::size_t CountLettersFgetc(std::FILE* f) {
    std::size_t letters = 0;
    int c;
    while ((c = std::fgetc(f)) != EOF) {
        if (std::isalpha(static_cast<unsigned char>(c))) {
            ++letters;
        }
    }
    return letters;
}
```

> [!warning] Не изобретайте стандартную библиотеку
> Вместо самодельного `('a' <= c && c <= 'z') || ('A' <= c && c <= 'Z')` используйте `std::isalpha` из `<cctype>` (а также `isdigit`, `isspace`, `isupper` …). Прежде чем писать утилиту, проверьте, нет ли готовой функции.
>
> 📎 Аргумент функций из `<cctype>` должен быть представим как `unsigned char` или равен `EOF`, поэтому для произвольного `char` нужен каст к `unsigned char`.

## 3. Буферизированное чтение: `fread`

### 3.1. Сигнатура

```cpp
std::size_t fread(void* buffer, std::size_t size, std::size_t count, std::FILE* stream);
```

«Прочитай из `stream` до `count` объектов размера `size` байт каждый и положи их в память, начиная с `buffer`.» Возвращается **число реально прочитанных объектов**: в конце файла их может оказаться меньше `count`, а `0` означает, что читать больше нечего.

| Параметр | Смысл | В примере |
|:---|:---|:---|
| `buffer` | Куда класть данные. `void*` принимает указатель любого типа, массив неявно преобразуется | `buffer` (массив `char`) |
| `size` | Размер **одного** объекта в байтах | `sizeof(char)` = 1 |
| `count` | Сколько объектов прочитать за раз | `kBufferSize` |
| `stream` | Откуда читать | `f` |

> [!info] Зачем `size` и `count` раздельно
> `fread` читает **объекты**: можно прочитать массив `int` (`size = sizeof(int)`) или одну структуру целиком (`count = 1`, `size = sizeof(MyStruct)`). Всего читается $\text{size}\times\text{count}$ байт. Запись структур «как есть» ломается из-за **выравнивания** (padding) — об этом [[03. Лекция - Структуры, объединения, выравнивание в памяти (padding) и побитовые поля (2026-09-25)|лекция 3]].

### 3.2. Цикл чтения

```cpp
#include <cctype>
#include <cstddef>
#include <cstdio>

constexpr std::size_t kBufferSize = 64;

std::size_t CountLettersFread(std::FILE* f) {
    char buffer[kBufferSize];
    std::size_t letters = 0;
    std::size_t read;
    while ((read = std::fread(buffer, sizeof(char), kBufferSize, f)) != 0) {
        for (std::size_t i = 0; i < read; ++i) {          // только прочитанные байты!
            if (std::isalpha(static_cast<unsigned char>(buffer[i]))) {
                ++letters;
            }
        }
    }
    return letters;
}
```

> [!tip] Именованная константа для размера
> Размер буфера встречается в нескольких местах: при объявлении массива, в вызове `fread` и т. д. Именованная константа `kBufferSize` позволяет изменить его в одном месте.

> [!warning] Цикл обработки — до `read`, а не до `kBufferSize`
> В последней порции буфер заполнен лишь частично; хвост массива содержит данные **предыдущей** итерации.

### 3.3. Почему `size_t`

`std::size_t` — беззнаковый тип для **размеров и количеств**, его возвращают `sizeof`, `fread`, `strlen`. На 64-битных платформах он 64-битный и гарантированно вмещает размер любого объекта в памяти. Для размеров принято использовать его, а не `int`.

## 4. Замер времени: `<chrono>`

> [!warning] Это не бенчмарк
> Однократный замер подвержен случайным выбросам, как измерение в лабораторной по физике. Правильно — **бенчмарк**: запустить код много раз и усреднить. На семинаре ради простоты время замерялось один раз.

```cpp
#include <chrono>
#include <iostream>

const auto start = std::chrono::steady_clock::now();
const std::size_t letters = CountLettersFread(f);       // замеряем только алгоритм
const auto end = std::chrono::steady_clock::now();

const std::chrono::duration<double, std::micro> elapsed = end - start;
std::cout << letters << " letters, " << elapsed.count() << " us\n";
```

- `steady_clock` — монотонные часы, подходят для измерения интервалов. `system_clock` — «настенное» время, которое может переводиться.
- Замеряется **только алгоритм**: открытие файла и вывод в интервал не входят.
- Результат (`letters`) **выводится**, иначе оптимизатор может выкинуть «бесполезные» вычисления.

## 5. Почему `fread` быстрее: разбор мифов

### 5.1. Результат

На файле в несколько десятков КиБ `fread` с буфером 64 байта оказался **примерно в 20 раз** быстрее `fgetc`.

### 5.2. Идея буферизации

**Буферизация** — общий приём: делать **дорогие операции реже, но крупнее**. Чтение из файла — дорогая операция: нужно обратиться к ОС (**системный вызов**, переход в ядро). Обращаться к ОС за каждым символом очень дорого, выгоднее за раз попросить тысячи байт (подробности — в курсе операционных систем).

### 5.3. Миф: «`fgetc` медленный, потому что читает по символу из файла»

> [!important] Это неправда
> У каждого `FILE` **уже есть внутренний буфер**, обычно несколько КиБ (стандарт не обязывает, но де-факто так). `fgetc` берёт символ **из этого буфера**, а к ОС обращается, только когда буфер опустел. Количество системных вызовов у `fgetc` и `fread` примерно одинаковое.

### 5.4. Откуда тогда разница

Каждый вызов `fgetc` — это вызов функции со служебной работой. Главная её часть — **блокировка `FILE`** (lock), чтобы другой поток не испортил его состояние во время чтения. `fread` тоже блокирует файл, но **один раз на порцию** из 64 байт, а не на каждый байт.

- Почему не в 64 раза? Число **системных вызовов** не изменилось (у обоих буфер), выросло только число **блокировок и вызовов функции**. Это заметная, но не главная часть общего времени, отсюда и усреднённый выигрыш ~20×.

> [!tip] 📎 Для любознательных
> В glibc есть `getc_unlocked` / `fgetc_unlocked` — версии без блокировки, для однопоточного кода. На MSVC аналог — `_fgetc_nolock`.

## 6. Как размер буфера влияет на скорость

### 6.1. Эксперимент

Файл увеличили до ~500 КиБ ($\approx 2^{19}$ байт) и прогнали `fread` с буферами $2^1, 2^2, \dots, 2^{19}$ байт:

```cpp
constexpr std::size_t kMaxBuffer = std::size_t{1} << 19;   // 512 КиБ
static char buffer[kMaxBuffer];                             // static: не на стеке

for (int power = 1; power < 20; ++power) {
    const std::size_t buffer_size = std::size_t{1} << power;
    std::rewind(f);                                         // ← вернуться в начало файла!
    // ... замер чтения с buffer_size ...
}
```

> [!warning] Ошибка, которую сделал ведущий
> Без `std::rewind(f)` первый прогон дочитывает файл до конца, и все следующие прогоны мгновенно получают `0` — замеры бессмысленны. После исправления выводы не изменились, но цифры стали честными.

### 6.2. Результат

```mermaid
flowchart LR
    A["буфер 2–64 Б: время падает почти вдвое с каждым удвоением"] --> B["1–8 КиБ: выход на плато"]
    B --> C["больше 8 КиБ: выигрыш в пределах погрешности"]
```

| Размер буфера | Поведение |
|:---|:---|
| Единицы–десятки байт | Время велико; каждое удвоение буфера почти вдвое ускоряет |
| Сотни байт–единицы КиБ | Ускорение замедляется |
| ≥ нескольких КиБ | **Плато**: дальнейшее увеличение почти ничего не даёт |

### 6.3. Почему плато

Время работы = **накладные расходы на вызовы и системные вызовы** + **обработка каждого байта**. Увеличение буфера уменьшает только первое слагаемое. Когда оно становится малым, время определяется вторым слагаемым — проходом по всем байтам, — и большой буфер уже не помогает. Это частный случай **закона Амдала**: ускорять имеет смысл ту часть, которая занимает основное время. 📎

### 6.4. Чем плох огромный буфер

- Большой массив **на стеке** может вызвать переполнение стека, особенно если функция вызывается часто или рекурсивно.
- Буфер в **динамической памяти** — это затраты на выделение и освобождение и промахи страниц (page faults).
- Платить памятью за выигрыш в пару процентов бессмысленно.

> [!important] Практическая рекомендация
> Выбирайте буфер **адекватного размера, порядка 1–8 КиБ**, кратный степени двойки (например, `4096`). Для своей задачи — **замерьте**.

## 7. Позиционирование в файле: `fseek`, `ftell`, `rewind`

| Функция | Что делает |
|:---|:---|
| `std::ftell(f)` | Текущая позиция (смещение от начала в байтах) |
| `std::fseek(f, offset, SEEK_SET)` | Перейти на `offset` от **начала** |
| `std::fseek(f, offset, SEEK_CUR)` | Сдвинуться на `offset` от **текущей** позиции |
| `std::fseek(f, offset, SEEK_END)` | Перейти на `offset` от **конца** (обычно `offset ≤ 0`) |
| `std::rewind(f)` | В начало файла; аналог `fseek(f, 0, SEEK_SET)` с дополнительным сбросом флага ошибки |

**Пример применения:** чтобы прочитать последние 100 байт большого файла, не нужно читать его целиком: `fseek(f, -100, SEEK_END)`, затем `fread`.

## 8. Запись и закрытие файлов

Функции записи симметричны чтению:

| Чтение | Запись |
|:---|:---|
| `fgetc(f)` | `fputc(c, f)` |
| `fread(buf, size, n, f)` | `fwrite(buf, size, n, f)` — возвращает число **записанных** объектов |

### 8.1. Утилита копирования файла

```cpp
#include <cstdio>

int main(int argc, char** argv) {
    if (argc != 3) {
        std::fprintf(stderr, "Usage: %s <src_file> <dst_file>\n", argv[0]);
        return 1;
    }
    std::FILE* src = std::fopen(argv[1], "rb");
    if (!src) {
        std::fprintf(stderr, "Cannot read file %s\n", argv[1]);
        return 1;
    }
    std::FILE* dst = std::fopen(argv[2], "wb");
    if (!dst) {
        std::fprintf(stderr, "Cannot write to file %s\n", argv[2]);
        std::fclose(src);                 // уже открытый файл тоже закрываем!
        return 1;
    }

    int c;
    while ((c = std::fgetc(src)) != EOF) {
        std::fputc(c, dst);               // int передаётся как есть
    }

    std::fclose(dst);                     // сбрасывает буфер записи на диск
    std::fclose(src);
    return 0;
}
```

- Подсказка `Usage` использует `argv[0]` — имя, под которым запустили программу.
- `argc != 3`: имя программы и два пути.

### 8.2. Почему обязательно `fclose`

> [!important] Запись тоже буферизирована
> `fputc` и `fwrite` пишут в **буфер** `FILE`, а на диск данные уходят, когда буфер заполнится (**flush**). Если программа завершится, не сбросив буфер, **последние данные могут потеряться**. `fclose` сбрасывает буфер и освобождает ресурс ОС; `fflush(f)` сбрасывает буфер, не закрывая файл.

**Правило:** после **успешного** `fopen` на **каждом** пути выхода из функции (в том числе на ранних `return` с ошибкой) должен быть `fclose`. Сейчас это делается вручную; позже в курсе будет **RAII** — идиома, при которой ресурс освобождается автоматически при выходе объекта из области видимости (так работают `std::ifstream` / `std::ofstream`).

## 9. C-API или `<fstream>`?

| | `<cstdio>` (C-API) | `<fstream>` (C++ потоки) |
|:---|:---|:---|
| Удобство с `std::string` | ❌ | ✅ |
| Работа с обычными массивами | ✅ естественно | ⚠️ менее удобно |
| Закрытие файла | вручную (`fclose`) | автоматически (RAII) |
| Скорость | высокая | **не обязательно** медленнее: это другой уровень абстракции |
| В первых лабах курса | ✅ рекомендуется | — |
